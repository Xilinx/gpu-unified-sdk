AMD GPU Unified SDK

A unified development toolkit for AMD Kria, Zynq UltraScale+, and Versal platforms — bringing the OpenGL ES, OpenCL, and Vulkan SDKs together in a single tree.

🚀 <strong>Overview</strong>

The AMD GPU Unified SDK consolidates the three previously separate GPU SDKs — OpenGL ES, OpenCL, and Vulkan — into one CMake project with shared support libraries and a common build system. It targets AMD embedded platforms including Kria, Zynq UltraScale+, and Versal systems, and ships out-of-the-box samples that customers can use as a starting point for new applications and to explore implementation possibilities.

✨ <strong>Key Features</strong>

  • 🎯 Comprehensive Sample Suite: Graphics (OpenGL ES / Vulkan) and compute (OpenCL) samples covering basic to advanced techniques.
  • 🏗️ Shared SDK Libraries: Common, EGL, GLES, and Vulkan helper libraries reused across all sample sets.
  • 🖥️ Multi-Platform Windowing: Wayland, X11, and framebuffer (fbdev) backends selectable at configure time.
  • ⚡ Performance Optimized: Leverages Mali 400 / Mali G78AE GPU hardware acceleration.
  • 🔧 Developer-Friendly: One CMake configuration builds the whole tree.

Project structure

  • cmake
    • modules - Additional CMake module wrappers
      • ecm - Extra CMake Modules (used in Wayland protocol compilation)
  • 3rdparty - Bundled third-party code
    • stb - stb_image.h single-header image loader (used by the Vulkan framework)
  • lib
    • sdk
      • common - Common graphical API agnostic helper classes
      • egl - EGL helper classes
      • gles - GLES helper classes
      • vulkan - Vulkan helper classes (RAII API)
      • vulkan-strings - Vulkan API identifiers to string convertor (debugging purposes)
      • vulkan-vendor-ids - GPU vendor name resolution from PCI ID global database (debugging purposes)
  • samples

    • vulkan

      • basic-compute - Compute-shader particle simulation rendered via graphics
      • triangle - Trivial triangle rendering
      • texture - Rotating textured quad (Vulkan image sampling)
      • spinning-cube - Textured 3D cube with depth buffering
      • multipass - Deferred shading with multiple subpasses
      • multisampling - MSAA rendering
      • mipmapping - Mipmap generation and sampling
      • astc - ASTC compressed texture sampling (with PNG fallback)
      • multithreading - Multi-threaded secondary command buffer recording

      All Vulkan samples select the windowing backend at runtime: –wayland VK_KHR_wayland_surface (under a compositor such as Weston) –display VK_KHR_display (direct DRM/KMS, no compositor) (no flag) auto: wayland if a compositor socket is present, else display

    • opengles - OpenGL ES samples, grouped by GLES version. All samples build on the SdkGlesFramework (lib/sdk/GlesFramework) except the standalone FBDEV-only EGLImage and OpenCL demos noted below.

      • opengl_es_2.0
        • trianglesample - Anti-aliased spinning triangle
        • alpha_depthsample - Alpha blending and depth testing
        • bbox - Bounding-box rendering with on-screen text
        • eglpreserve - EGL_BUFFER_PRESERVED swap behaviour
        • eglrenderingsample - EGLImage rendering (standalone, FBDEV only)
        • framebufferobject-fbosample - Render-to-texture via an FBO
        • multicubesample - Multiple textured spinning cubes
        • particlerenderingsample - GPU particle / molecule system
        • rotozoom - Rotation/zoom texture effect
        • shadowsample - Shadow mapping
        • texturemipmapsample - ETC mip-mapped textures
        • waveformsample - Animated waveform rendering
        • yuv2rgbsample - YUV-to-RGB colour conversion on the GPU
      • opengl_es_3.0
        • compute_particles - Compute-shader particle system
        • occlusion_culling - Hi-Z GPU occlusion culling
        • opencl_matmul - OpenCL matrix multiply (built only when OpenCL is found)

      Each sample is installed into bin/<sample>/ with its shaders/assets staged alongside the binary: per-sample shaders in Supportingfiles/, the shared font shaders in FontShaders/, and any extra data (models/, assets/, cl_kernels/). The samples load these with paths relative to the working directory, so run each one from its own install directory (e.g. cd bin/trianglesample && ./trianglesample).

      The windowing backend of the framework-based samples is selected at configure time with -D SDK_Platform=<wayland|x11|fbdev> (default wayland):

      • wayland - render through a Wayland (xdg-shell) surface; run under a compositor such as Weston.
      • x11 - render into an X11 window; run under an X server.
      • fbdev - render directly to the Linux framebuffer (EGL_DEFAULT_DISPLAY); run from a bare console. Exactly one backend is compiled, and only that backend's system libraries are linked. eglrenderingsample is a standalone EGLImage demo that manages its own surface; it is FBDEV only (run from a bare console). It builds independently of SDK_Platform (its build links X11 for the standalone codebase, but the sample is intended to run on the framebuffer).

    • opencl

      • hello-world-c - Array addition on the CPU only (no OpenCL, baseline reference)
      • hello-world-opencl - Array addition in an OpenCL kernel (scalar)
      • vector-hello-world - Array addition using vectorized OpenCL types
      • opencl-template - Minimal skeleton that runs a no-argument kernel
      • mandelbrot - Mandelbrot set generation written to a bitmap
      • mandelbrot-benchmark - Mandelbrot generation with image perturbation and timing
      • matrix-multiply - SGEMM benchmark suite (many kernel variants, CSV output)
      • sgemm - Single-precision matrix multiply (alpha*A*B + beta*C)
      • gaussian-filter - Gaussian blur of a PNG image
      • convolution-filter - User-defined 3x3/5x5 convolution filter
      • fir-filter - FIR (finite impulse response) image filter
      • sobel-filter - Sobel edge detection using vector loads (dX, dY, combined)
      • sobel-filter-no-vectors - Sobel edge detection, one pixel per work item
      • image-scaling - Image upscaling using OpenCL image objects and a sampler
      • integer-64-bit - Pixel sum/sum-of-squares using 64-bit ints and atomics
      • depth-map - Stereo disparity / obstacle detection from two images
      • adas-lane-detection - Lane visualization via Sobel edge detection (ADAS)
      • ml-classifier - Average-intensity feature + linear "Bright/Dark" classifier

      Most OpenCL samples read their inputs from assets/ (relative to the executable) and write results (e.g. output.bmp/output.png) into the current working directory.

Build

SDK application uses CMake as a build system and comes with most of the build time dependencies through the Google repo.

Instructions below assume that path to the repo checkout is at /path/to/src.

‍Important: No sample sets are built by default. Add a platform preset (e.g. -D SDK_PLATFORM_TARGET=versal-2ve-2vm) or per-API switches (e.g. -D SDK_BUILD_VULKAN=ON) to your cmake command — see Selecting what to build below.

Target configuration

Target build requires installed Yocto SDK with populated target sysroot. Assuming Yocto SDK ins installed at /path/to/yocto_sdk.

source /yocto/build/tmp/deploy/sdk/environment-setup-cortexa72-cortexa53-amd-linux
AMD_SDK=/path/to/yocto_sdk \
cmake \
-G Ninja \
-D CMAKE_BUILD_TYPE=Release \
-D CMAKE_TOOLCHAIN_FILE=sdk.cmake \
-D SDK_Platform=wayland \
-D SDK_PLATFORM_TARGET=versal-2ve-2vm \

SDK_Platform selects the OpenGL ES samples' windowing backend (wayland (default) | x11 | fbdev); see the samples/opengles notes above. SDK_PLATFORM_TARGET selects which sample sets are built (nothing by default); see Selecting what to build below.

Selecting what to build

Nothing is built by default — you must opt in to the sample sets you want, either with a target platform preset or with the explicit per-API switches.

Target platform preset

SDK_PLATFORM_TARGET enables a set of sample sets based on the SoC's GPU capabilities:

SDK_PLATFORM_TARGET GPU Sample sets enabled
none (default) — nothing (use the per-API switches)
versal-2ve-2vm Mali G78AE OpenGL ES 2.0 + 3.0, OpenCL, Vulkan
zynqmp Mali 400 OpenGL ES 2.0 only
# Build everything (Versal AI Edge Series Gen 2 / Mali G78AE)
cmake -G Ninja -D SDK_PLATFORM_TARGET=versal-2ve-2vm /path/to/sdk
# Build only the ZynqMP (Mali 400) examples -> OpenGL ES 2.0 only
cmake -G Ninja -D SDK_PLATFORM_TARGET=zynqmp /path/to/sdk

Per-API switches

All sample sets are OFF by default. These ON/OFF options override the platform preset, so any combination can be built:

Option Default Effect
SDK_BUILD_OPENGLES OFF Build the OpenGL ES samples
SDK_BUILD_OPENGLES_2_0 OFF Build the OpenGL ES 2.0 samples
SDK_BUILD_OPENGLES_3_0 OFF Build the OpenGL ES 3.0 samples
SDK_BUILD_OPENCL OFF Build the OpenCL samples
SDK_BUILD_VULKAN OFF Build the Vulkan samples

‍Enabling SDK_BUILD_OPENGLES without selecting a version builds both 2.0 and 3.0; use SDK_BUILD_OPENGLES_2_0 / _3_0 to pick one.

# Build only the OpenCL samples
cmake -G Ninja \
-D SDK_BUILD_OPENGLES=OFF -D SDK_BUILD_OPENCL=ON -D SDK_BUILD_VULKAN=OFF \
/path/to/sdk
# Build only the Vulkan samples
cmake -G Ninja \
-D SDK_BUILD_OPENGLES=OFF -D SDK_BUILD_OPENCL=OFF -D SDK_BUILD_VULKAN=ON \
/path/to/sdk
# Build only the OpenGL ES samples (both versions)
cmake -G Ninja \
-D SDK_BUILD_OPENGLES=ON -D SDK_BUILD_OPENCL=OFF -D SDK_BUILD_VULKAN=OFF \
/path/to/sdk

Only the support libraries for the enabled sample sets are built, so a subset build does not require the toolchain packages of the disabled APIs (e.g. a ZynqMP / OpenGL-ES-only build needs neither the Vulkan nor OpenCL SDK packages).

‍Note: Because these are cached CMake options, switching SDK_PLATFORM_TARGET after a first configure does not retroactively change the per-API option values. To switch platforms cleanly, configure into a fresh build directory, or pass the SDK_BUILD_* switches explicitly.

Compile

ninja

Running the OpenCL samples

Each OpenCL sample is installed into bin/<sample>/ together with its assets/ directory (kernels and input images). Because the samples load their kernels and inputs with paths relative to the working directory (e.g. assets/foo.cl, assets/input.bmp), run each sample from inside its own directory:

cd bin/gaussian_filter
./gaussian_filter

Notes:

  • Outputs are written to the current directory: filter/image samples produce output.bmp or output.png (the Sobel samples additionally write output-dX.bmp and output-dY.bmp).
  • Samples print OpenCL kernel profiling information (queued/wait/run time) on completion.

Sample-specific inputs and arguments:

  • matrix-multiply accepts command line options (run ./matrix_multiply -h for the full list, including -va to validate against a CPU reference and -csv <file> to dump results).
  • mandelbrot-benchmark and adas-lane-detection expect a 1024x1024 assets/input.bmp.
  • depth-map expects a stereo pair assets/left.bmp and assets/right.bmp.
  • sobel-filter expects an assets/input.bmp whose width is a multiple of 16.
  • gaussian-filter reads assets/input.png; all other image samples read assets/input.bmp.
  • integer-64-bit requires the cl_khr_int64_base_atomics device extension.
  • hello-world-c, hello-world-opencl, vector-hello-world, opencl-template and sgemm take no inputs and produce no image output.

🏗️ Framework Architecture

The unified SDK provides shared support libraries under lib/sdk/, reused by all sample sets:

  • common — Graphics-API-agnostic helpers (math, timing, image I/O, file utilities).
  • egl — EGL context/surface management for the OpenGL ES samples.
  • gles — OpenGL ES helper classes and the SdkGlesFramework windowing abstraction (Wayland / X11 / fbdev), font rendering, texture and matrix utilities.
  • vulkan — RAII-style Vulkan helper classes (context, swapchain, command buffers, assets) backing the Vulkan samples.
  • vulkan-strings / vulkan-vendor-ids — Debugging helpers that resolve Vulkan enums and GPU vendor names to human-readable strings.

The OpenCL samples build on the shared common image/bitmap helpers plus a thin OpenCL context/kernel management layer.

🔧 Adding New Samples

The build system is designed to be general. To add a new sample, copy an existing one in the relevant samples/<api>/ directory, rename the target in its CMakeLists.txt, and add an add_subdirectory(<newsample>) to the parent CMakeLists.txt. Place source files in the sample folder, shaders/kernels and data under the sample's Supportingfiles/, shaders/, assets/, or cl_kernels/ directory as appropriate.
